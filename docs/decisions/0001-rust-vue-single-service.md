# ADR 0001：Rust 后端与服务内托管 Vue

状态：已确认。

## 决定

PostWarden 后端使用 Rust；HTTP 服务采用 Axum，异步运行时采用 Tokio。管理界面使用 Vue，构建出的静态资源由同一个 Rust 服务提供，并在发布构建中嵌入可执行文件。无需为了管理页面单独部署 Nginx。

## 理由

项目是长期运行的自托管授权网关，需要清晰的模块边界、可控资源占用与便捷发布。Rust 适合构建单个服务发布物；Vue 足以实现简洁的管理界面。前后端仍在构建时分开开发，但发布时由同一服务提供，调用 Admin API 可保持同源。

## 主要备选

- Go：单二进制和并发支持同样契合；但项目选择 Rust，且 Rust 邮件库可满足目标 SMTP 能力。Go 标准 `net/smtp` 已冻结，若选 Go 仍需评估第三方库。
- Python/Django：管理后台开发更快，邮件功能成熟；部署运行时和依赖管理与本项目的单服务发布目标不完全吻合。
- TypeScript/Node.js：Nodemailer 的 SMTP 能力很完整，前后端可共用语言；但运行时与依赖链更大，不符合当前选定的 Rust 技术方向。
- React 或完整服务端渲染：都可实现界面；对以账号、Token、历史记录为主的管理页面没有明确收益，Vue 静态构建更直接。
- 独立 Nginx/前端容器：可用于大型部署，但会增加 MVP 的部署组件。已有反向代理仍可负责 TLS，并不负责必需的页面托管。

## 后果

构建过程需要 Rust 与前端工具链；发布时可以只运行 PostWarden 服务。直接对外开放时服务需提供 HTTPS，或部署在已有的可信 TLS 网关之后。具体依赖版本在工程初始化时锁定并验证。
